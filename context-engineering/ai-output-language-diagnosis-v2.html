AI / RAG / OUTPUT QUALITY

When AI Output Becomes Hard to Read

This is a real problem I encountered while interviewing at a company undergoing transformation.

At the time, the interviewer told me that they needed to generate fund analysis reports so that business users and clients could understand them more easily. In actual use, however, the AI-generated language was obscure and hard to follow. It was not obvious Chinese gibberish, but it was still difficult to read.

They were using an external general-purpose model, and the application involved the financial industry, so my first reaction was to fine-tune the model for the domain. Even after connecting a specialized knowledge base, the model might still fail to fully rely on retrieved content and instead answer from its own parametric knowledge.

The interviewer was convinced by my argument at the time. After the interview, though, I reviewed the problem more carefully: fine-tuning might indeed solve the problem, but it was not the optimal solution.

Start by Locating the Source of the Problem

Hard-to-understand AI output is not necessarily a sign that the model lacks capability. It may also be caused by the RAG pipeline, the original corpus, or generation controls.

Locating the source of the problem is not about adding more process. It is about determining where the change should be made. If the problem comes from the retrieval pipeline but the model is modified through fine-tuning, it is usually difficult to achieve stable results.

You should first use the same batch of questions for a controlled comparison and observe three situations separately:

01Give the model only the question.
02Give the model evidence that has been organized in advance.
03Connect the complete RAG pipeline.

01 · Retrieved context

If the output is still hard to follow after giving the model organized evidence, the problem may come from the original corpus or generation control. If the response is clear when evidence is provided alone but becomes worse after connecting the complete RAG pipeline, the retrieval context needs to be checked. For example, poor chunking, too much retrieved content, or noise mixed into the reranking results can all cause the model to stitch together incomplete sentences, resulting in repeated content or broken references.

02 · Source corpus

If the output directly reuses long sentences from annual reports, announcements, or policy documents, the problem mainly comes from the style of the corpus. Sentence boundaries, heading structure, table content, and professional terminology can be processed before indexing. For relatively stable scenarios, documents can first be extracted into an intermediate structure such as “metric — value — time — scope — evidence source,” and reports can then be generated from those structured facts.

03 · Generation control

If the retrieved evidence is clear and the content is not fragmented, but the model still generates long sentences, passive voice, and a high density of technical terms, the problem is closer to generation control. At this point, an output schema, an audience definition, tone constraints, and few-shot examples can be used to standardize the way the model expresses the result. If necessary, temperature and output length can be adjusted.

A report can use a structure such as “Conclusion, Evidence, Risks, and Items to Verify,” but it should not become a fixed template that is forcibly applied to every problem. Different problems require different output fields, otherwise the results can easily become mechanical.

Factual Accuracy and Readability Need to Be Evaluated Separately

Factual accuracy concerns whether the evidence is sufficient and whether the key conclusions in the answer are supported by the retrieved content. It does not tell you whether the answer is easy to understand.

Readability cannot be judged only by sentence length. You should first use automated metrics to screen for syntactic complexity, P95 sentence length, connective density, the proportion of technical terms, unexplained terminology, referential ambiguity, and repetition rate. These metrics help identify expression risks, but they cannot directly serve as the final conclusion.

Then, have an independent evaluator extract the conclusion, subject, amount, time, conditions, and risks from the answer and compare them with a reference answer. This can help verify whether the user truly understands the answer, rather than merely judging whether the text looks short on the surface.

Finally, business users should provide manual scores or compare the old and new versions. At the same time, record comprehension accuracy, the time required to find the conclusion, and whether manual rewriting is still needed.

Only when automated metrics, semantic comprehension tests, and human evaluations all meet the established baseline can the output be considered readable. If it does not pass, trigger one constrained rewrite. If it still does not pass after rewriting, fall back to a structured summary.

Factual support and readability must be scored separately. Smoother wording must not be used to conceal omitted facts, and simplifying the language must not change the original conclusion.

When to Use Fine-Tuning

LoRA or fine-tuning is worth evaluating only when prompt design, retrieval governance, structured intermediate representations, and constrained generation have all reached a bottleneck, and when a sufficiently large number of high-quality samples with a stable style has already been accumulated and de-identified.

Fine-tuning is more suitable for solving problems involving stable domain terminology, output formats, and task behavior. It should not be used as a general fix for hard-to-read language.

Returning to the original fund analysis report scenario, the correct steps are to first confirm whether the problem comes from the retrieved content, the original corpus, or generation control, and then decide whether fine-tuning is necessary. The advantage of doing this is that it can effectively control costs: the scope of change is smaller, and the results are easier to verify,
