Memory lifecycle / forgetting

How Should Long-Term Memory Forget?

Three approaches to keeping stale context out of current answers, and a general engineering model for deciding what to keep, downgrade, replace, archive, or delete.

Retrieval Memory state Retention

1. Define the Scope First

Short-term context serves the current conversation. Long-term memory persists across conversations and may influence future responses.

When a conversation becomes too long, the system may remove older messages or use summaries and compression to control the context window. Long-term memory works across sessions. It stores information that may be retrieved later and used again.

These two systems solve different problems. Short-term context asks how much information can fit in the active window. Long-term memory asks whether information saved in the past should still affect the system later.

Short-term context

The current conversation

Its main constraint is the size of the active context window.

Long-term memory

Across conversations

Its main question is whether saved information should still influence later work.

Long-term memory also has no fixed storage format. It can live in a vector database, a knowledge graph, a relational database, Markdown files, a hierarchical structure, or several of these at the same time. Most memory stores are simply different implementations of the same long-term persistence problem.

Whatever the storage method, every memory system eventually has to deal with forgetting. That part cannot be avoided, and it has to be designed carefully.

2. Why Focus on Forgetting in Long-Term Memory

Long-term memory becomes less useful when it only stores information without maintaining it.

As the memory store grows, retrieval is more likely to bring back irrelevant content. Old and new information may appear together. A plan that has already ended may still be mistaken for an active task.

This creates two problems. The system returns more historical noise by default, and that noise continues to consume the context window.

Deletion is also more complicated than removing a visible record. One memory may already have been turned into a summary, embedding, cache entry, or search index. If the system only removes the text shown in the user interface, other copies may still be retrieved.

The real question for long-term memory is this. Should this information still influence the current response?

Forgetting can happen at several stages. A memory can receive a lower retrieval rank, making it less likely to be recalled. It can be excluded during context assembly, so it no longer enters an answer automatically. A newer version can replace it in current results while the old version remains available as history. Eventually, the memory can be archived, deleted, or anonymized according to a retention policy.

Forgetting therefore does not always mean immediate deletion. It can also mean reducing influence, changing status, or removing a memory from the normal retrieval path.

3. Three Typical Approaches

Consider a simple example. An AI remembers that “Xiao Wang will travel to Shanghai for a business trip next Friday.” A few months later, Xiao Wang says, “The trip has been moved to next month.”

The system now has to answer several questions.

  • Has the original trip information been used recently?
  • Does “moved to next month” refer to the Shanghai business trip?
  • Should the old record be downgraded, archived, or deleted?

For a person, this looks like checking an old note and crossing out the outdated date. For an AI system, the old note may exist in several forms and may already have been used in previous retrieval results.

POluz / Ombre-Brain

Time Decay and Archiving

The core idea of POluz/Ombre-Brain is to gradually lower the priority of memories that have not been used for a long time.

The system considers factors such as memory age, importance, retrieval count, and protection status. It periodically recalculates how active each memory is.

When a memory remains unused, its ranking gradually falls. It becomes less likely to appear in normal retrieval results, then leaves the default working set, and eventually moves into an archive area.

This approach treats recent usage as an important signal. Information that has been used recently is more likely to remain in the active set.

Benefit

Historical memories do not receive the same level of exposure forever. Unused content gets a clear path out of default retrieval, so ordinary answers are less likely to contain irrelevant history.

Limit

Inactivity does not prove irrelevance. A fact may be important even if it has not been accessed for years. Time decay cannot prove that a fact is false or has been replaced.

Time decay is useful for deciding whether a memory should be easy to recall. It cannot handle fact conflicts or version replacement on its own.

omnirexflora-labs / omnimemory

Semantic Replacement and Memory Evolution

The focus of omnirexflora-labs/omnimemory is the relationship between new and old memories.

When new information arrives, the system tries to determine whether it duplicates, supplements, corrects, or conflicts with existing content.

  • Duplicate information can be skipped.
  • Supplementary information can be merged.
  • A confirmed new fact can move the old version out of current results.
  • Uncertain cases can keep both versions until the relationship becomes clearer.

This approach treats memory as a set of evolving versions. The value of an old record may change when new information appears, so the system needs to preserve the relationship between them.

Benefit

It reduces the chance of old and new facts appearing together. Current answers are more likely to use the newer version, while the old record does not have to disappear completely.

Limit

Semantic matching can be wrong. Similar wording may describe different events, and newer information may be less reliable than the old information. Without source, timestamp, and confirmation status, automatic replacement can discard the correct version from current results.

Semantic replacement mainly handles relationships between memories. It does not solve the problem of memories that have never been updated but have gradually lost their value because nobody uses them.

Qizhan7 / imprint-memory

On-Demand Maintenance and Proactive Cleanup

Qizhan7/imprint-memory treats forgetting as an ongoing maintenance task.

The system stores conversations and later looks for stale memory by considering creation time, importance, and retrieval count. Maintenance tools can lower a memory’s importance, protect it from decay, mark it for forgetting, or delete it.

This approach treats memory quality as something that can be checked after the original write operation. The system does not have to rely entirely on the decision made when the memory was first created.

Benefit

A user or maintenance task can identify memories that have not been used for a long time and decide whether to downgrade, protect, archive, or delete them. A dry_run preview makes it possible to inspect the result before applying changes.

Limit

Maintenance must actually run. If the scheduled task fails, or nobody reviews stale memories, old content remains in the system. Lowering importance changes retrieval behavior but does not prove that the underlying fact is no longer valid.

Taken together, these three approaches address three different concerns. Time decay manages memory activity. Semantic evolution manages relationships between versions. Proactive maintenance manages later review and cleanup.

4. General Engineering Practices

There is no single forgetting formula that works in every system. A practical design usually needs several separate engineering decisions.

  • Recent usage helps determine whether a memory should remain near the top of retrieval results.
  • New information helps determine whether an old version still describes the current situation.
  • Protection, withdrawal, and deletion requests determine whether normal decay rules may continue to affect a memory.

These decisions can be combined into a general lifecycle.

01Current and usable. The memory can participate in normal retrieval.
02Long unused. It enters a cooling period.
03Influence decreases. Default retrieval becomes less likely.
04Replaced by newer content. It becomes a historical version.
05Relationship is unclear. It enters conflict handling.
06Retention limit is reached. It is archived, deleted, or anonymized.

This lifecycle still needs clear boundaries. Time decay measures recent use. Semantic evolution handles relationships between old and new content. Maintenance tools provide the entry point for review and cleanup.

None of them can independently determine whether a fact is true or whether data should be deleted.

A memory system should therefore separate at least four concerns.

01 / STORAGEContent and provenance
02 / RETRIEVALPriority and ranking
03 / STATECurrent, replaced, disputed, or archived
04 / BUSINESSProtection, withdrawal, deletion, and anonymization

The storage layer keeps the actual content, source, timestamps, and version relationships. The retrieval layer ranks memories according to relevance, time, and usage. The state layer records whether a memory is current, replaced, disputed, pending review, or archived. The business layer handles protection, withdrawal, deletion, and anonymization.

A single score can help rank memories. It should not represent truth, validity, retrieval priority, and retention permission at the same time.

A high score does not prove that a fact is correct. A low score does not mean that the data can be deleted. A memory that was recently retrieved is not necessarily valid forever.

A more reliable system keeps these questions separate.

  • What exactly does the memory say?
  • Where did it come from?
  • Is the fact still valid?
  • Is it useful for the current task?
  • Should the system bring it up automatically?
  • Does the system still have permission to retain it?

The three approaches can then work together. Time decay can reduce irrelevant retrieval, semantic evolution can manage old and new versions, and maintenance tools can provide explicit review and cleanup.

5. Closing Summary

Long-term memory has no single required storage format. Vectors, graphs, documents, relational tables, and hierarchical structures can all support the storage layer.

The more important question is how the system controls memory over time.

Good long-term memory should know when to reduce a memory’s influence, when to stop using it in current answers, when to keep it only as historical context, and when to remove it from the system completely.

This note compares the approaches as engineering patterns. It focuses on system behavior and design boundaries rather than judging the projects themselves.
