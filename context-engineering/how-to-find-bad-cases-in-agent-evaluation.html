AI / AGENT EVALUATION / BAD CASE DETECTION

How to Find Bad Cases in Agent Evaluation

I recently came across the open-source ai-evaluation-skill project. It uses skills to automate evaluation, much like my own approach. Where we differ is in how bad cases get discovered and assessed.

The project follows a well-engineered pipeline: a fixed Benchmark, an Evaluation Runner that calls the product's real entry point, an LLM-as-Judge that scores outputs across multiple Rubric dimensions and flags veto candidates, mandatory human review plus a 10% stratified sample, a Bad Case ledger, manual root-cause attribution across eight layers, and finally repair with feedback into the Benchmark. The engineering discipline here is solid. The Rubric scoring, the strict review gates, and the closed-loop Bad Case process are all done well.

Where I think it can be supplemented is the active discovery of bad cases. The project relies heavily on Judge scores and human review to surface problems. If a case produces a high-quality output but takes a problematic execution path, the Judge may never flag it. There is no runtime behavior anomaly detection based on traces. Root-cause attribution happens manually after the fact, in the Bad Case closed-loop phase. Online signals such as user feedback, support tickets, and monitoring data are imported into the ledger passively rather than being extracted automatically from live sessions. And the human review queue has no priority ordering. Every mandatory review item carries equal weight.

My approach adds four progressive layers of automated detection before the Judge scoring and human review stage. Each layer narrows the scope using deterministic rules and weak signals, so human attention is spent only on cases that genuinely need judgment.

Layer 1: Format and Structure Validation

This is the cheapest layer and the right place to start automation.

The ai-evaluation-skill Runner records execution status, trace IDs, and errors. But it does not have a dedicated structure validation layer that filters out cases which clearly did not complete. Every case, including those where the LLM returned nothing, the trace is missing fields, or the Agent flow did not finish, still enters the Judge phase. When the Judge faces an empty output or an incomplete trace, the score itself becomes unreliable.

My approach compares the structured fields of the case and the trace directly, without involving any model:

  • Whether case_id exists
  • Whether trace_id exists
  • Whether expected_route and actual_route are comparable
  • Whether expected_path is hit

This filters obvious execution failures: the LLM did not return, the Trace is missing fields, the Agent flow did not complete, or the final reply is empty. These problems do not need a model to judge. They are bad cases by definition.

Compared with ai-evaluation-skill: its Judge has to handle both "did it run to completion" and "is the output good" at the same time. I intercept deterministic structure problems with rules in Layer 1, so the Judge only needs to process cases that actually completed.

Layer 2: Behavior Anomaly Detection

I will use my own project as an example here. You can adapt these checks to your own business context.

My project is not a typical tool-calling agent. It uses an agent loop architecture I orchestrated myself: a ChatService while loop, Agent execution, a returned NextAction, and then the next Agent.

The ai-evaluation-skill Judge scores output quality across Rubric dimensions such as accuracy, relevance, and task completion. It cares about whether the final answer is good. But agent evaluation has a special problem: the answer may be acceptable, but the process may be wrong. For example, a high-risk input eventually reaches a safety template, but the route is not input safety interception. It gets blocked by quality inspection only after generation. Looking at output quality alone, this case would be marked as "answered correctly." But it is actually a risk case.

The ai-evaluation-skill Bad Case closed-loop does include "tool calling" as a root-cause layer, but that is used for manual attribution after the fact, not for automated detection at runtime.

Behavior anomalies I detect include:

  • The same Agent executes more than N times consecutively
  • The same NextAction appears repeatedly
  • The actual retry count exceeds maxRetry

This layer is valuable because it catches bad cases where "the result is correct but the process is abnormal." Rubric scoring cannot cover this. Rubric evaluates output, not execution path. An agent is not a pure function. The execution path itself is part of quality.

Compared with ai-evaluation-skill: its bad case discovery depends on the Judge scoring output quality. If the output is good, the case will not be flagged as a veto candidate. My Layer 2 specifically catches "good output, wrong process" cases using rule-based detection on traces, with no model judgment required.

Layer 3: Optional Low-Confidence Detection

This layer is optional. It is not required.

Only when the volume of high-risk cases is large enough that human or Oracle review becomes a bottleneck do I run an independent validation path as a shadow check. The main pipeline generates once, and the shadow validation pipeline makes an independent judgment. The first run executes the complete main pipeline. The second run only executes the high-risk decision nodes. If the two runs show large differences, the case is marked as low-confidence.

But this mark is only used to adjust review priority. It is never used to directly classify a bad case. A large difference means "this case deserves to be looked at first," not "this case is definitely wrong."

If all current high-risk cases can be directly and finally confirmed by humans, this layer is skipped. There is no reason to use it for its own sake.

Why not run it on everything? Not just because of cost. Consistency checking suits high-value decision points: crisis identification, follow-up decisions, RAG evidence conflicts. These are places where errors have high impact, so shadow check helps order the review queue. Running it on every ordinary answer would amplify model randomness and produce low-value noise.

The shadow pipeline can also be wrong. Many differences fall into "multiple reasonable interpretations": the user's expression is ambiguous and both routes have basis, the main pipeline has more context while the shadow input may differ, or one route chooses to ask a follow-up while the other thinks it can answer directly. So the output can only be a priority signal, never a conclusion.

Compared with ai-evaluation-skill: its human review uses "mandatory set plus 10% sampling," and every mandatory review item carries equal weight in the queue. There is no priority ordering. Its low-confidence signal comes from the uncertainty field that the Judge self-reports, which is essentially the same model expressing doubt about its own score. My Layer 3 uses an independent shadow pipeline for a second judgment. The difference between two paths is more reliable than a single model self-reporting uncertainty. And this difference is only used to order the review queue. When high-risk cases are few, humans can review them directly and this layer is unnecessary. When the volume becomes too large to handle, it helps surface the most likely problematic cases first.

Layer 4: Implicit Feedback

This can only serve as a weak signal. It cannot be used directly as a failure label.

In the ai-evaluation-skill Bad Case workflow, failure signal sources include "user feedback, support tickets, online monitoring, A/B tests, or retrospective imports." But these are all passively imported. Someone has to organize the online problem and write it into the ledger. The system itself does not automatically extract bad case signals from live sessions. Its primary bad case source remains the fixed Benchmark in offline evaluation.

My Layer 4 automatically extracts supplementary signals from live sessions. For example, right after the Agent answers, the user immediately asks again: "You didn't answer my question just now," or "In other words..." Or the user repeats the same question with similar semantics. This may indicate that the first answer did not solve the problem. But it could also just be a normal follow-up question, so the more reasonable handling is:

01Implicit feedback enters the bad case candidate pool.
02Explicit feedback, trace analysis, or offline evaluation confirms the bad case.

The system combines sessionId, caseId, time window, semantic similarity, whether new information was added, negative user expressions, and the previous round's trace to make a judgment. If it confirms that the answer did not solve the problem, a skill converts it into a regression case by filling in expected_route, expected_path, must_include, and diagnosis_hints. It then enters regression evaluation.

Do not feed this directly to a PolicyLearningService as a negative reward. That would easily produce false positives on normal multi-turn conversations.

Compared with ai-evaluation-skill: its online signals are manually imported into the ledger, and bad cases come primarily from the fixed Benchmark. My Layer 4 automatically extracts weak signals from live sessions and generates candidates, which then go through a confirmation process before becoming regression cases. A fixed Benchmark will overfit and cannot cover long-tail problems. Automatically detected implicit feedback from online sessions is an important supplement. And it follows the same "candidate then confirmation" two-stage judgment, never treating weak signals as direct conclusions. This is consistent in spirit with ai-evaluation-skill's rule that "the Judge can only flag veto candidates, and final veto requires human confirmation."

Putting It Together

The four layers, side by side with ai-evaluation-skill:

Dimension ai-evaluation-skill Four-Layer Approach
Primary bad case source Fixed Benchmark offline evaluation Benchmark plus automatically extracted online implicit feedback (Layer 4)
Obvious execution failures Enter the Judge phase, scored by Rubric Intercepted directly by Layer 1 structure validation, never reach the Judge
"Good result, wrong process" Rubric scores output quality; path anomalies require manual post-hoc attribution Layer 2 automatically detects behavior rules based on traces
Low-confidence signal Judge self-reports uncertainty, triggers mandatory review Independent shadow pipeline double-run; differences only order review priority
Human review queue Mandatory set plus 10% sampling, no priority Direct confirmation when volume is low; Layer 3 shadow check orders priority when volume is large
Online signals Manually imported into the ledger System automatically extracts candidates, confirmed before becoming regression cases
Root-cause identification Manual attribution across 8 layers in the Bad Case closed-loop Layers 1 and 2 automatically locate via rules; humans only handle the candidate pool
Signal reliability Judge score plus human review gate Signal strength decreases per layer; candidate and confirmation are separated; weak signals never become direct conclusions

The core point is this: ai-evaluation-skill does solid work in evaluation engineering discipline. Its Rubric scoring, strict review gates, and Bad Case closed-loop are all well built. Its limitation is not that it does something wrong. It is that bad case discovery relies too heavily on the Judge scoring output quality and on human review. It lacks automatic supplementation for execution path anomalies, online weak signals, and review efficiency.

My four-layer approach is not meant to replace it. It adds an automatic screening layer before its Judge plus human review pipeline: deterministic structure validation as the safety net, rule-based behavior anomaly detection, optional shadow check to optimize review efficiency, and online implicit feedback to supplement coverage. Each layer knows what it can and cannot do. Human attention is concentrated on cases that genuinely require judgment. Combining both approaches is what agent evaluation should look like.
