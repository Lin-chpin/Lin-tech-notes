Memory, Context, and Information Lineage

A practical way to think about layered memory in AI agents, from short-term conversation state to durable facts, event logs, content hashing, and traceable updates.

Agent memoryState managementContext assembly

1. First, Separate Memory from Context

Memory is state stored outside a single request so it can be reused later. Context is the input that a model actually sees during one specific request.

They are related, but they serve different purposes.

01Raw messages, structured facts, and audit logs
02Selection, compression, ordering, and token budgeting
03Context assembled for the current request
04Generation, quality checks, fact extraction, and state updates
05New raw messages, structured facts, and audit logs

Real context engineering has to answer four questions:

  1. What information is worth keeping?
  2. What information is relevant to this request?
  3. Which source and version should win when facts conflict?
  4. How do we compress context without losing safety-critical information?

2. The Foundation of Context Management: Layered Memory

A memory system should not be one giant history bucket.

Different kinds of information have different lifetimes, trust levels, and usage patterns. They should be managed separately.

Short-term memory

Continuity

What was happening in the active conversation a moment ago?

Long-term memory

Reusable facts

Which confirmed information should still influence future work?

Public knowledge

External reference

What rules, documents, or domain knowledge can the system reuse?

2.1 Short-Term Memory Preserves Continuity, Not Authority

Short-term memory answers a simple question:

What was happening in this conversation a moment ago?

A typical implementation isolates it with a sessionId. In multi-user, multi-case, or concurrent environments, that boundary may also need userId and caseId.

Redis is a reasonable place to keep this data as a short-lived cache. It can quickly restore recent context when a user has just corrected something, added missing information, or left the app and returned later.

A common configuration is a 24-hour TTL. If Redis expires, the system can rebuild the recent conversation from MySQL, assuming the raw messages were stored durably.

Redis is an acceleration layer. It should not be the only source of truth.

Short-term memory should preserve recent raw messages, including:

  • user input;
  • assistant replies;
  • unfinished follow-ups;
  • current task state;
  • recent routing and safety state;
  • temporary evidence related to the current issue.

The raw form matters because later operations may need it for state extraction, question tracing, or error diagnosis.

A summary may disagree with the long-term state. When that happens, the system should record the summary’s source and version, inspect the original messages, and treat the validated long-term state as authoritative.

Short-term memory also has to handle concurrency:

  • the same user operates on mobile and web at the same time;
  • a background summarization job has not finished;
  • multiple service instances process the same session;
  • an older summary tries to overwrite a newer one.

Without versioning or compare-and-set semantics, an old summary can silently replace a newer state.

Short-term memory is a good fit for recent conversation turns, the current task goal, recent routing decisions, and temporary evidence. It is a poor place to store durable facts.

2.2 Long-Term Memory Stores Fact State, Not a Polished Summary

Long-term memory should turn reusable information into state that can be verified and updated.

A safer flow looks like this:

Raw message
    ↓
MemoryExtractor
    ↓
Structured patch
    ↓
StateReducer
    ↓
CaseState
    ↓
Audit records and derived indexes

The model only proposes a structured patch. It cannot directly overwrite facts in the database.

StateReducer checks the source, format, version, user boundary, and case boundary. It does not decide whether a medical statement is clinically true.

For example, if a user says:

I developed a rash after taking a certain medication.

The system may extract:

rash_after_medication = candidate

It should not silently turn that into:

the user is allergic to that medication

The user’s statement, the model’s inference, and a professionally verified conclusion have different authority levels.

When old and new facts conflict, the system should preserve both sources and record a conflict state. It should not select one simply because it looks more similar or more recent.

A later user correction, withdrawal, or confirmation can then drive an explicit state transition.

Important facts should remain traceable to at least:

sourceMessageId
version
status
object or scope
confirmationSource
createdAt
updatedAt

That allows the system to answer questions such as:

  • Where did this fact come from?
  • Which model or rule produced it?
  • Did it replace an older version?
  • Was it confirmed, withdrawn, or still only a candidate?

2.3 Public Knowledge Is a Source, Not User Memory

Public knowledge includes documents, standards, product information, and other reusable domain knowledge.

Long-term memory answers:

What happened to this user, case, or object?

Public knowledge answers:

What is the normal rule or background knowledge in this domain?

A RAG system can technically store long-term memory, but the business semantics are different.

Some long-term memories are natural-language preferences or historical summaries. Users may describe the same thing with different wording later, so semantic search can be useful.

Exact patient facts, configuration values, thresholds, and other authoritative fields should use structured storage and explicit validation.

The current context may need all three sources:

Short-term memory
        +
Long-term facts
        +
Public knowledge

Their authority, update process, and deletion rules must remain separate.

3. DeepSeek Harness: Recoverable Runtime State Through Event Logs

I recently studied the architecture of DeepSeek Harness. The important idea is not simply to add another Memory class.

It is to turn the Agent’s runtime into a traceable event stream.

In its public architecture, the session is built around an append-only, typed event log. Model-visible message history can be derived from that log. The model adapter, tool registry, session log, and Agent Loop are all replaceable through plugins. DeepSeek Harness Architecture Session Subsystem

This solves a runtime problem:

  • Where is the Agent in its execution?
  • What did the model actually see?
  • Which tools were called?
  • What did those tools return?
  • Can the task continue after a restart?

Before thinking about this, it is tempting to store recent messages and intent state directly inside the Agent process.

That works in a single-user demo.

Once the service restarts, multiple sessions run concurrently, or several instances process the same case, the state can disappear or leak between conversations.

Short-term memory should therefore not exist only as a temporary in-process object.

Recent messages, tool calls, model responses, and task state should have recoverable records. The current Prompt is only a projection of these records.

Compression needs the same discipline.

Raw Session Events
        ↓
Context projection or compaction result
        ↓
Current model-visible context

The compaction result is replaceable derived data. The raw event log remains the source for reconstruction.

Principle one

Separate state from Agent code

Conversation records should not disappear when a process is restarted or replaced.

Principle two

Rebuild what the model sees

Current context should be derived from traceable records rather than treated as the only copy.

Boundary

Logs do not solve everything

Recovery still depends on durable writes, ordering, idempotency, and reliable replay logic.

If compression fails, the service restarts, or multiple instances switch ownership, the system still has a path back through the event log.

4. MyContext: Content Hashing and Information Lineage

MyContext focuses on a different problem.

Information may come from many places. The system needs to keep collecting, processing, searching, and returning it while preserving the original evidence.

Data sources
    ↓
Incremental ingestion
    ↓
Raw records
    ↓
Structured facts and relationships
    ↓
Full-text, vector, and graph indexes
    ↓
Retrieved results with source references

4.1 Content Hashing Detects Changes Under the Same ID

In an earlier design, I used sourceMessageId for deduplication.

That is insufficient when the same ID can point to changed content.

For example, the first version of a record says:

The project is using MySQL 8.

A later version says:

The database has moved to PostgreSQL.

If the message ID does not change, the system may treat the record as already processed. The long-term state then remains stale.

Adding contentHash lets the system detect content changes under the same ID and trigger a new extraction, version replacement, or conflict process.

The graph layer should also distinguish between the original source unit and the retrieval chunk derived from it. Each derived chunk should retain its content hash and processing lineage.

4.2 Information Lineage Explains Where a Fact Came From

The system should preserve more than the final fact.

It should also know:

  • which source produced it;
  • which extraction task generated it;
  • which model and Prompt version were used;
  • whether it replaced an older version;
  • which indexes need to be rebuilt if the source changes.

A complete lineage chain may look like this:

Original message
    ↓
Extraction task
    ↓
Candidate fact or structured patch
    ↓
StateReducer validation
    ↓
CaseState version
    ↓
Full-text, vector, or graph index

A useful implementation can track fields such as:

sourceMessageId
extractionRunId
modelVersion
promptVersion
pipelineVersion
factVersion
supersedesId
createdAt

This lets the system answer:

  • Where did this memory come from?
  • Which model or rule produced it?
  • Did it replace an earlier version?
  • Which indexes need to be rebuilt?
  • What derived data must be removed when the user deletes the source?

This is what makes memory auditable instead of merely searchable.

5. A Compact End-to-End Example

Consider a generic project fact.

The user says:

This project currently runs on MySQL 8 and is deployed on Alibaba Cloud.

MemoryExtractor creates a candidate patch:

database.engine = MySQL 8
deployment.provider = Alibaba Cloud
status = CANDIDATE
sourceMessageId = msg-001

The user confirms the information, so both facts move to CONFIRMED.

Two weeks later, the user says:

The database has moved to PostgreSQL, and the deployment has moved to AWS.

The system creates new versions instead of overwriting the old records:

FactStateMeaning
MySQL 8SUPERSEDEDHistorical version
Alibaba CloudSUPERSEDEDHistorical version
PostgreSQLCONFIRMEDCurrent active fact
AWSCONFIRMEDCurrent active fact

The next model request should receive:

Database: PostgreSQL
Deployment: AWS

The old MySQL and Alibaba Cloud records remain available for auditing and historical reconstruction. They do not participate in ordinary retrieval.

If Redis expires, the system can rebuild the current state from MySQL and the event history.

If an old vector index still contains “MySQL 8,” the status gate should block that stale result before it reaches the model.

The model proposes a change. The user or an approved source confirms it. The reducer creates a new version. Current context reads active facts, while audit records preserve the change history.

The same pattern works for project configuration, user preferences, customer profiles, order status, and other domains.

6. Summary

DeepSeek Harness focuses on what the Agent is doing and how to recover it.

MyContext focuses on where information came from and how to keep processing and tracing it.

For a general Agent memory system, these ideas can be combined into four responsibilities:

01 / EVENT LOGRecord the runtime process
02 / LONG-TERM STATEPreserve reusable facts
03 / CONTENT HASHDetect changes under the same source ID
04 / LINEAGEExplain where each fact came from

Context assembly decides what the model should see in the current request.

Compression is one governance mechanism inside that process. It should never become the only source of truth.

How to Validate the Design

A minimal validation plan should check four cases:

  • after the project switches to PostgreSQL, the current Prompt no longer uses MySQL;
  • after Redis expires, the same current state can be rebuilt from MySQL;
  • stale index results are blocked by the fact status;
  • every active fact can be traced back to its source message and version.

Implementation boundary. The layered memory, persistent event records, and auditable CaseState described here are production design patterns. They should not be presented as shipped capabilities unless the corresponding storage, replay, and validation paths exist in code.
